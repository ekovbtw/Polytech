### О проекте
(CVE-2024-21413 Moniker Links) - это критическая уязвимость (с оценкой 9.8 по шкале CVSS) удаленного выполнения кода (RCE) и кражи учетных данных, обнаруженная в почтовом клиенте Microsoft Outlook. 
### COM
Для начала необходимо разобраться в том, что такое COM ==(Component Object Model)==. COM — это технология Microsoft, представляющая собой стандарт взаимодействия между программными компонентами (объектами, такими как: Word.Application, Excel.Application, Outlook.Application). Она определяет набор правил, по которым приложения и службы предоставляют свои объекты другим программам, независимо от языка программирования, на котором они написаны. Благодаря этому приложение, написанное на одном языке программирования, может создавать объекты другого приложения и вызывать их методы, даже если оно написано на другом языке. В контексте данной работы COM представляет интерес потому, что Outlook использует его для обработки специальных объектов — **Moniker**. Именно особенности взаимодействия Outlook с COM стали одной из причин возникновения уязвимости CVE-2024-21413.
### Почему вообще появился COM
Изначально, Microsoft было необходима возможность взаимодействия различных приложений друг с другом. Например: открыть объект Word документа в Excel, а другие приложения — использовать функциональность друг друга без необходимости знать их внутреннюю реализацию.
### Пример использования COM
`New-Object -ComObject Word.Application` - создает COM объект файла Word. 
Таким образом используя лишь PowerShell можно создать COM-объект Word.Application в памяти. В результате чего PowerShell передает строку "Word.Application" в COM Runtime, COM Runtime обращается к стандартному пути в реестре Windows: "HKEY_CLASSES_ROOT/Word.Application" (в данном случае HKEY_CLASSES_ROOT - специальная ветка реестра Windows, предназначенная для хранения информации о COM объектах), если такой раздел существует значит он зарегистрирован (имеет CLSID), *подробнее о HKEY_CLASSES_ROOT описано в [[DESCRIBE HKEY_CLASSES_ROOT]]*. В конце COM Runtime возвращает ссылку на созданный объект.
Заметим, что COM изначально никакого представления не имеет о том, что это за объект Word.Application ведь его нет в памяти. 
### Поиск нужного объекта
Продолжаем рассматривать команду: `New-Object -ComObject Word.Application`. Как мы знаем, чтобы безошибочно распознать объект используется GUID (Global Unique Identifier) — уникальный 128-битный идентификатор. Он гарантирует, что созданный код не совпадает ни с каким другим. Для поиска COM объектов используется CLSID (Class Identifier) — подраздел GUID, уникальный идентификатор COM класса. Как уже описано выше, COM ищет директорию "Word.Application" в ветке реестра HCKR, в которой находится соответствующий CLSID. CLSID используется в дальнейшей работе COM. Уникальность CLSID состоит в том, что ProgID (Word.Application можно изменить) не уникален, в отличие от CLSID, который имеет 32 шестнадцатеричных символа (например, `{21EC2020-3AEA-1069-A2DD-08002B30309D}`), отвечающие за идентификатор COM компонента. 
То есть внутри COM происходит примерно следующее: 
```
CLSID clsid;

// Получить CLSID по ProgID
CLSIDFromProgID(L"Word.Application", &clsid);

// Создать объект
CoCreateInstance(clsid, ...); 
```
### Создание нужного объекта
После получения CLSID COM вызывает функцию CoCreateInstance(CLSID). CoCreateInstance не создает самостоятельно объект, а обращается к COM серверу (программа, содержащая реализацию COM-классов, то есть описание типа объектов, например [[COM класс - Word.Application]] ), который в последствии создает объект (экземпляр класса COM, [[Отличие COM-класса от COM-объекта]]) с таким CLSID. 
```
# например
CLSID
└── {000209FF-0000-0000-C000-000000000046}
      │
      └── LocalServer32
            C:\Program Files\Microsoft Office\...\WINWORD.EXE # COM-сервер
```
 После создания объекта его нужно вернуть программе для дальнейшей работы.  
```
Объект Word:
	данные  
	код  
	документы 
	окна
```
Можно было бы вернуть весь объект, но тогда клиент увидел бы внутреннее устройство Word (*инкапсуляция*). Для того, чтобы вернуть такой объект для дальнейшей работы, который бы не давал программе обращаться к внутренним полям (данные, код ... ) нужно вернуть указатель на интерфейс (`pInterface`), чтобы вызывать код COM-объекта через специального посредника (указатель `pInterface` ведет на VTABLE) — таблица интерфейса (VTABLE — виртуальная таблица указателей на функции COM-объекта). В итоге мы получаем, что сам объект находится в памяти отдельно, а VTABLE неявно связана с ним. В COM определенно, что любой объект должен иметь как минимум один интерфейс. Им является интерфейс IUnknown [[Интерфейсы в COM]].
То есть в функции CoCreateInstance() происходит примерно следующее: 
```
CoCreateInstance(
    CLSID,
    ...,
    IID_IUnknown,
    &pointer
);
```
Если резюмировать, то: `CoCreateInstance()` создает экземпляр COM-класса (COM-объект с помощью COM-сервера) и возвращает указатель на запрошенный интерфейс этого объекта (например, `IUnknown` или другой). Сам объект не возвращается, поскольку COM скрывает его внутреннюю реализацию (инкапсуляция) и предоставляет доступ только через интерфейсы.

### IDispatch
Проблема: скриптовые языки (Python, JS, VBS и так далее) компилируют код "на лету", что мешает программе изначально знать структуру VTable. 
Для решения такой проблемы был создан интерфейс IDispatch (automation или "позднее связывание"). IDispatch — интерфейс, родитель которого — IUnknown. Вместо того чтобы забивать VTable десятками разных методов (`Save`, `Print`, `Open`), разработчики добавили в VTable всего один главный рабочий метод — **`Invoke`**.
В VTable интерфейса `IDispatch` (после обязательной тройки `IUnknown`) идут 4 метода, но ключевыми являются два:
1. **`GetIDsOfNames`** — переводит текстовое имя функции в числовой идентификатор (DISPID).
2. **`Invoke`** — выполняет саму функцию по её идентификатору.
3. **`GetTypeInfoCount`** (Получить количество описаний типов)
4. **`GetTypeInfo`** (Получить само описание типа)
Если в скрипте написать object.save("report.docx") интерпретатор выполняет два скрытых запроса к интерфейсу IDispatch: Сначала спрашивается "есть ли метод "save"" у объекта во внутренних таблицах, если есть, то возвращается DISPID (Dispatch Identifier — уникальный числовой идентификатор, для нахождения и вызовов методов, свойств в COM-объекте), иначе возвращается соответствующий ошибке запрос, вторым шагом интерпретатор упаковываем аргумент (в данном случае "report.docx") в универсальный специальный массив (массив структур VARIANT) вызывается метод Invoke — вызывает метод save по полученному DISPID с упакованным аргументом. В конце Invoke возвращает результат обратно. 

Сравнение: Обычный COM (VTable) vs IDispatch

| Критерий             | Обычный COM (Раннее связывание)                        | IDispatch (Позднее связывание)                                            |
| -------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------- |
| **Как вызывается**   | Напрямую по номеру строки в VTable                     | Непрямо: Сначала по имени ищем ID, потом вызываем `Invoke`                |
| **Скорость работы**  | **Очень быстро** (один прыжок по адресу в памяти)      | **Медленнее** (тратится время на текстовый поиск и упаковку параметров)   |
| **Гибкость**         | Низкая (нужно знать структуру на этапе написания кода) | **Максимальная** (можно управлять объектом, ничего не зная о нем заранее) |
| **Где используется** | C++, Delphi, C# (внутренние системные компоненты)      | Скрипты, Python, 1С, макросы VBA в Excel/Word                             |

Чтобы разработчикам не приходилось выбирать между скоростью и универсальностью, большинство современных COM-объектов (например, в MS Excel) делают **двойными**.
Это значит, что их VTable устроена так: сначала идут методы `IUnknown`, затем 4 метода `IDispatch`, а сразу за ними — прямые методы объекта (`Save`, `Close`).
- Если объект вызывает программа на C++, она игнорирует `IDispatch` и прыгает сразу на метод `Save` (быстро).
- Если объект вызывает скрипт на Python, он использует методы `IDispatch` для вызова по имени (гибко).

### Moniker
Именно в этом разделе начинаются пересечения с выбранной уязвимостью. Moniker("кличка" или "прозвище") — специальный COM-объект, который хранит текстовое имя другого объекта, а также знает: где его найти, как запустить и как правильно загрузить его данные. Главная задача Moniker — перейти из текстовой строки(пути к файлу или системой команды) в готовый к работе указатель на объект. Раньше для создания COM-объекта мы использовали его ProgID --> CLSID и так далее (создавали пустой, новый объект определенного COM-класса), а с помощью Moniker мы можем создать (не обязательно пустой) объект, который уже находится на жестком диске. Без Moniker загрузить не пустой объект можно следующем путем: 
- Вручную запустить Excel через CLSID.
- Найти нужный метод интерфейса для открытия файла и передать туда путь.
- Найти метод для поиска нужного листа.
Работа с Moniker-объектом осуществляется при помощи интерфейса IMoniker. Всего в IMoniker (включая унаследованные методы) входит более 20 методов. Их можно логически разделить на несколько функциональных групп [[Методы в интерфейсе IMoniker]].
В этой уязвимости Outlook получает строку (ссылку), создает на ее основе Moniker и доверяет ему выполнить дальнейшие действия.
